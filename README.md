# Sedona By Team AEGIS

**LLM-assisted vendor risk assessment for new IT services — running on your own machine.**

Sedona reads a vendor-supplied HECVAT questionnaire, compares every control against your
institution's approved policy documents, optionally weighs supporting evidence such as a SOC 2
report, and produces a gap analysis as PDF, PPTX and CSV.

Sedona runs on **Linux with an NVIDIA GPU** (llama.cpp) and on **macOS with Apple Silicon**
(Ollama). The vector store is always in-process, and every uploaded document is parsed, chunked
and embedded locally on both platforms.

> **Decision support, not a compliance verdict.** Sedona's output is generated by a language model
> and must be reviewed by a qualified staff member before it informs any procurement, contracting or
> risk decision.

> **Where the chat model runs decides whether vendor data leaves the machine.** On Linux, and on
> macOS with a local model, nothing does — that is the default Linux deployment's whole point. But
> the macOS default is `gemma4:31b-cloud`, and a `-cloud` tag runs on **Ollama Cloud**: the control
> text, the vendor's answers and the retrieved policy excerpts are sent to `ollama.com` to be
> scored. Confirm that is acceptable for your data before assessing a real vendor. To stay entirely
> local, change one line in `BACKEND/config.py` — see
> [Choosing the model](#choosing-the-model). Embeddings are always computed locally, on both
> platforms.

Built for Murdoch University IT by Team Aegis (TD01), Murdoch University Dubai — Aditya Jain,
Fahadullah Ahamedullah, Ryan Alex, Sakina Shabbar, Saleh Khan and Izaan Shumaiz.

## Platform support

Sedona supports two deployments. They share all application code and differ only in what serves
the two models — selected automatically by platform, so neither normally needs configuring.

| | **Linux** (reference) | **macOS** |
| --- | --- | --- |
| Backend (`SEDONA_LLM_BACKEND`) | `llama_cpp` | `ollama` |
| Serves the models | two llama.cpp servers, ports 8000 + 8001 | one Ollama daemon, port 11434 |
| Chat model runs | on the local GPU | on Ollama Cloud by default; locally if you choose a local tag |
| Embeddings run | locally | locally |
| Hardware | NVIDIA GPU required | Apple Silicon |
| Install compiles anything? | yes — a CUDA toolkit and llama.cpp, 10–30 min | no |

Users never touch the host on either. Sedona is operated from a browser on any operating system.

### Linux

The reference deployment is **Ubuntu 20.04 LTS (server)** on a GPU-backed VM. Newer releases such
as 22.04 and 24.04 are expected to work — the version-specific work in the installer is all about
tolerating *older* hosts — but they have not been tested.

The installer builds everything it needs inside the project folder, so it works on an older or
locked-down Ubuntu host without root: nothing is installed system-wide, `sudo` is never required,
and deleting `.runtime/` undoes the whole installation.

**Prerequisites.** The installer sets up the runtime stack for you, but it cannot provide these:

| Requirement | Notes |
| --- | --- |
| **NVIDIA GPU + driver** | If no GPU is visible, setup stops with an explanation rather than quietly producing a slow CPU-only build. |
| **Node.js 18+ with npm** | The one dependency the installer will not fetch for you. |
| **`curl`** | Required. `wget` is accepted as a substitute while installing, but the launcher's health checks use `curl` only. |
| **Outbound internet** | First install only. |
| **A normal (non-root) user account** | Do not run `start.sh` as root. |

Check them before installing anything:

```bash
node --version      # v18, v20 or v22+
npm --version       # any version
curl --version      # required
nvidia-smi          # a table listing at least one GPU
```

CUDA itself is **not** a prerequisite — the installer detects your GPU and driver and installs a
matching toolkit inside the project folder.

### macOS

macOS runs on **Ollama** instead of llama.cpp. One local daemon on port 11434 serves both models
through the same OpenAI-compatible API the Linux path uses, so no application code changes: it
resolves `*-cloud` tags against your ollama.com account and runs everything else locally on Metal.

Nothing is compiled on this path. There is no CUDA toolkit, no llama.cpp build, no Xcode toolchain
and no multi-gigabyte weight download when you use a cloud model — so a first install is minutes
rather than the better part of an hour.

**Prerequisites:**

| Requirement | Notes |
| --- | --- |
| **Apple Silicon Mac** | Intel Macs are untested. |
| **[Ollama](https://ollama.com/download)** | The one dependency the installer will not fetch for you. The daemon must be running — the menu-bar app, or `ollama serve`. |
| **An ollama.com account** | Only for `-cloud` models. `ollama signin` once. Not needed if you run a local model. |
| **Node.js 18+ with npm** | Same as Linux. |
| **`curl`** | Ships with macOS. |

Check them before installing anything:

```bash
node --version      # v18, v20 or v22+
ollama --version    # any recent version
ollama list         # must print a table, not a connection error — that proves the daemon is up
```

No NVIDIA driver, no CUDA and no `SEDONA_FORCE_CPU` are involved on macOS. Those apply only to the
`llama_cpp` backend, and the installer skips their steps entirely.

### Tested on

| Component | Linux (reference) | macOS |
| --- | --- | --- |
| OS | Ubuntu 20.04 LTS (server) | macOS 26.6, Apple Silicon |
| Accelerator | NVIDIA T4-8Q (8 GB VRAM slice) | Ollama 0.32.15 (Metal + Ollama Cloud) |
| vCPUs / RAM | 24 vCPUs / 64 GB | — |
| Python | 3.12+ (installed for you) | 3.12+ (installed for you) |
| Storage | vector store, ~2.8 GB of weights, reports | vector store and reports; ~275 MB for the local embedding model |

On the Linux VM, running other GPU workloads on the same host at the same time is not recommended —
8 GB of VRAM is workable for the chat model, but tight.

### Network requirements

On **Linux**, the first installation is the only stage that needs the internet, to download Python,
the CUDA toolkit, the model weights (~2.8 GB) and the frontend packages. **An air-gapped first
installation is not supported.** After that, Sedona runs entirely locally.

On **macOS with a `-cloud` model**, outbound internet is needed for *every assessment*, not just at
install time, because each control is scored on ollama.com. Choosing a local tag restores the
Linux behaviour of running offline after setup.

Sedona does not require a VPN. By default the web interface listens on all interfaces, so it can be
reached from other machines on the network, while the API listens on localhost only and is reached
through the frontend. Access control is per-user sign-in — everything is behind an account, so add
network-level restrictions only if your deployment calls for them.

## System at a glance

- React/Vite frontend in `FRONTEND/src`
- FastAPI application in `FRONTEND/api.py`
- HECVAT parsing, retrieval, assessment, follow-up and reporting in `BACKEND`
- Local llama.cpp chat and embedding servers (Linux), or a local Ollama daemon (macOS)
- Chroma vector store for retrieval
- Local users, role-based access, cookie sessions and CSRF protection

On Linux a running system is four processes, all managed by `start.sh`:

| Port | Component | Role |
| --- | --- | --- |
| 8000 | Chat engine | Runs `gemma-3-4b-it` — judges whether each control has a gap |
| 8001 | Embeddings engine | Runs `nomic-embed-text-v1.5` — powers retrieval |
| 8080 | API server | Authentication, sessions, uploads, reports, health |
| 5173 | Frontend | The web interface |

On macOS the first two rows collapse into one **Ollama daemon on port 11434**, which answers both
`/v1/chat/completions` and `/v1/embeddings`. That leaves two processes for `start.sh` to manage —
the API and the frontend. Ollama is shared user infrastructure, so Sedona never starts it, never
adopts it and never stops it; `start.sh` only checks that it is answering.

All ports can be changed through environment variables. The vector store runs in-process, so there
is no separate service to start for it.

Embeddings run locally on both platforms, and they are the same `nomic-embed-text-v1.5` f16 weights
either way — so a `chroma_db/` built on one platform is readable on the other. On Linux the weights
come from Hugging Face during installation; on macOS Ollama pulls them.

## Getting started

### Linux

On a machine with nothing installed:

```bash
./start.sh
```

That is the whole procedure. If `start.sh` cannot find a Python that has Sedona's dependencies,
it installs everything first, then starts the services.

### macOS

Install [Ollama](https://ollama.com/download) and make sure it is running, then:

```bash
ollama signin                     # once, for -cloud models only
./start.sh
```

`start.sh` installs Python, the dependencies and the frontend packages, and pulls the two model
tags — then starts the services. To pull the models yourself first:

```bash
ollama pull gemma4:31b-cloud      # the chat model (a few hundred bytes: it runs on ollama.com)
ollama pull nomic-embed-text      # the embedding model (~275 MB, runs locally)
```

If Ollama is not answering, `start.sh` stops and tells you to start it rather than trying to take
it over. Start it from the menu-bar app or with `ollama serve`, then re-run.

To install without starting anything, or to see what is missing:

```bash
./scripts/bootstrap.sh            # install whatever is missing
./scripts/bootstrap.sh --check    # report what is missing, change nothing
./scripts/bootstrap.sh --force    # re-run every step from scratch
```

`--check` exits **1** on a fresh machine. That means "components are missing", not that the check
failed; re-run it after installing and it should exit 0.

Then open the URL `start.sh` prints and sign in.

Do not run `start.sh` as root.

### Choosing the model

The chat model is **one line in `BACKEND/config.py`**:

```python
LLM_MODEL   = os.environ.get(
    "SEDONA_LLM_MODEL",
    "gemma4:31b-cloud" if _OLLAMA else "gemma-3-4b-it",
)
```

Change the `"gemma4:31b-cloud"` string to any tag `ollama list` reports, then restart the API with
`./start.sh --restart-api`. `SEDONA_LLM_MODEL` overrides it without editing the file, which is
handy for trying one out.

| Tag | Runs | Notes |
| --- | --- | --- |
| `gemma4:31b-cloud` | Ollama Cloud | The default. Same Gemma lineage the system prompt was tuned against. |
| `gpt-oss:120b-cloud` | Ollama Cloud | The strongest option. Keeps its reasoning in a separate response field, so report output is unaffected. |
| `gemma4:e4b-mlx` | locally, on Metal | **No data leaves the machine.** |
| `gemma3:4b` | locally, on Metal | The same weights the Linux deployment serves. |

Anything ending in `-cloud` sends prompt content to ollama.com and needs `ollama signin`; anything
else runs on your Mac. Pull a tag before selecting it — Sedona reports a model that was never
pulled at startup and in `/health`, rather than failing one control at a time.

The embedding model is the line below it. Changing it invalidates the existing vector store: the
knowledge base must be re-ingested, because vectors from two different embedding models are not
comparable.

On the `llama_cpp` backend these two lines are display labels only — llama.cpp serves whatever GGUF
`LLM_GGUF_PATH` points at.

### Creating the first administrator

Sedona has no default account and no default password. The first administrator is created from three
environment variables, read **only once** — on the first start, while the user database is still
empty. Export them before that first start:

```bash
export SEDONA_BOOTSTRAP_ADMIN_USERNAME="sedona-admin"
export SEDONA_BOOTSTRAP_ADMIN_PASSWORD="ExamplePassphrase-2026!"
export SEDONA_BOOTSTRAP_ADMIN_DISPLAY_NAME="Sedona Administrator"
```

Those values are examples. Choose your own and never deploy with a placeholder password.

- The username and password must be set **together**, or the API stops rather than creating a
  half-configured account.
- Password: at least 12 characters, using at least three of lowercase, uppercase, digits and
  symbols. Username: 3–64 characters.
- Export the variables directly — **do not `source .env.example`**.
- Remove them from the environment once the first start succeeds.

Self-service sign-up is always available from the sign-in page and cannot be turned off, but it
only ever creates a Viewer, which can do nothing until an admin promotes it.

### Completing the setup

Installation is not finished when the sign-in page loads. A new system has an **empty knowledge
base**, and assessments stay blocked until an administrator adds the policy documents.

1. Sign in as the bootstrap administrator at the address `start.sh` printed.
2. Open the admin-only **Knowledge Base** page and upload the approved policy PDFs and
   `HECVAT_Template.xlsx` shipped with the release.
3. On the **User Access** page, create an Assessor account for each person who will run assessments,
   and Viewer accounts for reviewers.
4. Confirm `curl "http://localhost:8080/health?strict=1"` returns 200. A 503 on a new installation
   almost always means step 2 has not been done.
5. Run one assessment end to end and confirm PDF, PPTX and CSV all download.

### What to expect on first start

On **Linux**, the first install is much slower than every start after it — it downloads Python, the
model weights and the frontend packages, and compiles the GPU runtime. The compile alone takes
10–30 minutes and warns you about this before it starts; it is compiling, not hung. After that, a
normal start takes about a minute, driven almost entirely by loading the models onto the GPU.

On **macOS**, nothing is compiled and a cloud model has no weights to download, so the first install
is a few minutes: Python, the dependencies, the frontend packages and a ~275 MB pull of the local
embedding model. Later starts take seconds, because Ollama is already running and the cloud model
has nothing to load.

A healthy start prints a `SEDONA Risk Console` banner and three green readiness lines — engines,
API, frontend — then the address to open. The two engines are reported together on one line, so
three lines is correct, not four. On macOS the engine line reads "already healthy; reusing them",
because the Ollama daemon is always something Sedona finds rather than starts.

## What the installer sets up, and where

Everything lands **inside this folder**. Nothing is written to `$HOME`, nothing needs sudo, and
deleting `.runtime/` undoes all of it.

| Path | Contents |
| --- | --- |
| `.runtime/venv` | the Python environment and Sedona's dependencies |
| `.runtime/conda` | package manager, only used to fetch the CUDA toolkit (Linux) |
| `.runtime/cuda` | the CUDA toolkit, used once at install time (Linux) |
| `.runtime/.stamps` | which steps have completed |
| `models/` | the chat and embedding model weights (Linux) |

On macOS the model weights are Ollama's, kept in `~/.ollama` and shared with everything else you
use Ollama for — so `models/`, `.runtime/conda` and `.runtime/cuda` are never created.

Steps run in order and each one is skipped when the thing it installs already works:

| Step | Does | Runs on |
| --- | --- | --- |
| `10-python` | finds a suitable Python or installs one, then creates the environment | both |
| `20-requirements` | installs `BACKEND/requirements.txt` | both |
| `30-cuda` | detects the GPU and installs a matching CUDA toolkit | Linux only |
| `40-llama` | builds the GPU inference runtime | Linux only |
| `50-models` | downloads the GGUF files (Linux) or runs `ollama pull` (macOS) | both |
| `60-frontend` | installs the frontend npm packages | both |

On macOS, `./scripts/bootstrap.sh --check` never lists `30-cuda` or `40-llama`: with Ollama serving
the models there is nothing to compile, so those steps are skipped rather than failed.

A step is judged by whether it actually works, not by whether a marker file exists, so a
half-finished install repairs itself on the next run rather than being skipped.

### If there is no GPU

On **Linux**, the installer **stops with an explanation** instead of quietly producing a CPU-only
build. A full assessment takes roughly four hours on CPU against minutes on a GPU. To ask for it
deliberately:

```bash
SEDONA_FORCE_CPU=1 ./scripts/bootstrap.sh
```

This does not apply to macOS. `SEDONA_FORCE_CPU` only affects the `llama_cpp` backend; Ollama
handles Metal and cloud execution itself.

## Running Sedona

| Command | Effect |
| --- | --- |
| `./start.sh` | Start whatever is down, reuse whatever is healthy. |
| `./start.sh --adopt` | Same, but take ownership of services already running, so `Ctrl-C` stops them. |
| `./start.sh --stop` | Stop this checkout's API and frontend. |
| `./start.sh --stop --engines` | Also stop the chat and embedding servers (`llama_cpp` backend only). |
| `./start.sh --restart-api` | Replace only the API process, after a backend code change. |

`start.sh` reuses any of the four components that are already healthy, so a bare run is also a safe
health check. It only ever manages its own services — a second Sedona elsewhere on the host is never
disturbed.

`Ctrl-C` stops only what that terminal owns. A service that was already running was reused, not
owned, and keeps going — use `--adopt` to take ownership, or `./start.sh --stop` from any terminal.
Closing the terminal window is not a clean shutdown.

Backend changes need `--restart-api`. Frontend changes hot-reload; no restart needed. Changing the
model in `config.py` is a backend change, so it takes effect on `--restart-api`.

On Linux, stopping the engines means the models reload on the next start, which takes minutes
rather than seconds. Leave them running unless you need the GPU back.

On macOS there are no engines of Sedona's to stop. `--engines` has nothing to act on: the Ollama
daemon is shared user infrastructure, so Sedona never starts it, never adopts it with `--adopt`,
and never stops it. Stop Ollama the way you started it — quit the menu-bar app, or `Ctrl-C` the
`ollama serve` you ran.

### Configuration

Paths, ports, model files and data locations are all environment-overridable — see `.env.example`.
The useful ones:

| Variable | Purpose |
| --- | --- |
| `SEDONA_LLM_BACKEND` | `llama_cpp` or `ollama`; defaults by platform |
| `SEDONA_LLM_MODEL` | override the chat model without editing `config.py` |
| `SEDONA_EMBED_MODEL` | override the embedding model (re-ingest afterwards) |
| `SEDONA_PYBIN` | use a specific Python instead of searching |
| `SEDONA_DATA_DIR` | relocate all persistent state at once |
| `SEDONA_API_PORT` / `SEDONA_FRONTEND_PORT` | change ports (default 8080 / 5173) |
| `SEDONA_LLM_PORT` / `SEDONA_EMBED_PORT` | change engine ports (8000 / 8001 under `llama_cpp`; both 11434 under `ollama`) |
| `SEDONA_MODEL_DIR` | where the GGUF files live (`llama_cpp` only) |
| `SEDONA_LOG_DIR` | where the log files are written |
| `SEDONA_COOKIE_SECURE` | set true when Sedona is served over HTTPS |
| `SEDONA_FORCE_CPU` | build without CUDA (`llama_cpp` only) |

Paths are anchored to the project root, so it does not matter where you launch from.

Configuration is a deployment task done on the host — there is no settings screen inside the app.

## How an assessment works

1. An administrator adds the approved policy documents and the HECVAT template to the knowledge base.
2. An assessor uploads a filled HECVAT and names the vendor or service.
3. The assessor may attach the vendor's SOC 2 report or other supporting PDFs. These stay isolated to
   that session and never enter the institution-wide knowledge base.
4. Sedona assesses each applicable control. A control it cannot judge reliably is flagged for manual
   resolution rather than guessed at.
5. The assessor answers or skips the follow-up questions and resolves any flagged controls.
6. Sedona generates the CSV, PDF and PPTX outputs from one set of findings, so they cannot disagree.

The PDF and CSV carry every control in full. The PPTX is a fixed-length executive briefing and does
not grow with the size of the assessment.

### What you can upload

| Input | Accepted | Notes |
| --- | --- | --- |
| HECVAT | `.xlsx`, `.xlsm` | Checked at upload, so a bad workbook is caught straight away rather than becoming a failed session. |
| Supporting evidence | PDF only | Optional, and isolated to its session. |
| Policy documents | PDF + `HECVAT_Template.xlsx` | Added once by an administrator. |

Files are capped at 50 MB. Only Admin and Assessor accounts can upload.

### Results and reports

Gaps are reported at five severities — **VERY HIGH**, **HIGH**, **MEDIUM**, **MINOR** and **LOW** —
and can be filtered on the Results page. Reports download as `RiskAssessment_<Vendor>.pdf`,
`RiskBriefing_<Vendor>.pptx` and a matching CSV, so no renaming is needed before sharing. Downloads
only work once the session is complete.

Only one assessment runs at a time across the whole system. An assessment keeps running if you close
the browser — reopen the session from the History page to get back to it. Saved answers can be
resumed any time; the initial scan cannot be paused, only cancelled, and cancelling deletes that
session's data.

## Roles and security

| Role | Can |
| --- | --- |
| **Admin** | Everything an Assessor can, plus the User Access and Knowledge Base screens |
| **Assessor** | Upload, run assessments, answer follow-ups, generate reports, manage their own sessions |
| **Viewer** | Read-only, and only for completed sessions assigned to them |

Every user signs in with their own account. Passwords are stored as salted hashes, the session cookie
cannot be read by page scripts, and requests that change data carry a CSRF token. Sessions expire
after eight hours by default. Self-registered accounts always arrive as Viewers and must be promoted
by an admin.

The interface needs JavaScript and cookies enabled. A current Chrome or Safari is recommended.

## Health and logs

`GET /health` reports the real state of the chat server, the embedding server and the vector store,
plus whether an assessment can actually run. Add `?strict=1` to get a 503 when something is wrong:

```bash
curl "http://localhost:8080/health?strict=1"
```

It names the active backend, and under `ollama` it also reports whether each model tag is actually
pulled — a daemon that is running but missing the tag would otherwise pass a port check and then
fail every control:

```json
"services": {
  "backend": "ollama",
  "llm":        {"port": 11434, "reachable": true, "model": "gemma4:31b-cloud",  "model_present": true},
  "embeddings": {"port": 11434, "reachable": true, "model": "nomic-embed-text", "model_present": true}
}
```

Logs are written to `logs/` by default: `llm.log` for the two engines, `api.log` for the backend and
`frontend.log` for the web interface. On macOS `llm.log` is not written — Sedona does not launch
Ollama, so Ollama keeps its own logs (`~/.ollama/logs/server.log`).

### Troubleshooting

Both platforms:

| Symptom | Check |
| --- | --- |
| `npm not found` | Install Node 18+ and re-run. |
| Ports already in use | `./start.sh --stop --engines` frees them cleanly before relaunching. |
| Health degraded, assessments rejected | Almost always an empty knowledge base — add the policy documents. |
| `No Python with Sedona's dependencies found` | Run `./scripts/bootstrap.sh`. |

Linux only:

| Symptom | Check |
| --- | --- |
| Setup stops on GPU detection | No NVIDIA GPU was found. Provision one, or accept `SEDONA_FORCE_CPU=1` and hours per assessment. |
| The build looks hung | The GPU runtime compile takes 10–30 minutes and says so before it starts. |
| An engine never reports ready | Read `logs/llm.log` before assuming the whole system failed. |

macOS only:

| Symptom | Check |
| --- | --- |
| `Ollama is not answering on port 11434` | The daemon is down. Open Ollama.app, or run `ollama serve`, then re-run `./start.sh`. |
| `the 'ollama' command was not found` | Install Ollama from <https://ollama.com/download>. |
| `model '<tag>' is not pulled` | `ollama pull <tag>`. Confirm the spelling against `ollama list`. |
| `could not pull '<tag>'` on a `-cloud` model | Cloud models need an account: `ollama signin`. |
| Every control fails with a connection error mid-assessment | A `-cloud` model needs internet for each control. Check connectivity, or switch to a local tag. |
| Assessments are slow and the fans are loud | You selected a local model, not a cloud one. That is expected — a 31B cloud model does not run on your Mac. |

## Known limitations

- **Accuracy is a target, not a measured result.** 90% correctness against a manually reviewed
  reference is the goal, but no reference dataset or results ship with this release.
- **Timing depends on the size of the HECVAT.** Report generation is quick when no follow-ups were
  answered, but each answered follow-up triggers another pass, so a fully answered 88-control HECVAT
  can take twelve minutes or more.
- **No automatic CPU fallback.** On Linux, CPU is available only by deliberately setting
  `SEDONA_FORCE_CPU=1`.
- **The macOS default sends data off the machine.** `gemma4:31b-cloud` is scored on ollama.com, so
  the offline-after-install property of the Linux deployment does not hold unless you switch to a
  local model. Cloud inference also needs internet during every assessment, not just at install.
- **The two platforms will not produce identical findings.** They run different chat models, so
  scores and wording differ between them. Embeddings and retrieval are identical.
- **Model downloads are not checksum-verified.**
- **The from-scratch install has not been formally recorded.** Sedona has been run and tested on
  the machine above, but a clean-machine installation has not been carried out and documented
  end to end against this release.

Sedona does not make a vendor compliant. It produces decision support that requires qualified
human review.
