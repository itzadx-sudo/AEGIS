# Sedona By Team AEGIS

**LLM-assisted vendor risk assessment for new IT services — running entirely on your own Linux box.**

Sedona reads a vendor-supplied HECVAT questionnaire, compares every control against your
institution's approved policy corpus, optionally weighs session-scoped vendor evidence such as a
SOC 2 report, and produces a reviewed gap analysis as PDF, PPTX and CSV.

The language model, the embedding model and the vector store all run on the host. Once installed,
no vendor data leaves the machine and no external model API is called.

> **Decision support, not a compliance verdict.** Sedona's output is generated by a language model
> and must be reviewed by a qualified staff member before it informs any procurement, contracting or
> risk decision — particularly for insufficient evidence, controls with no usable model result, SOC 2
> exceptions, scanned documents, and manual resolutions.

## Platform support

**Sedona runs on Ubuntu Linux.** The reference deployment is **Ubuntu 20.04 LTS (server)** on a
GPU-backed VM, and the installer is built specifically so that an older, locked-down Ubuntu host is
a first-class target rather than an obstacle:

- **No `sudo`, no PPAs, nothing installed system-wide.** Ubuntu 20.04 ships Python 3.8, which is too
  old for Sedona. Rather than asking for root to add a deadsnakes PPA, `10-python` installs a private
  Miniforge Python under `.runtime/`. Deleting that folder undoes the entire installation.
- **Built against your glibc, not someone else's.** The published CUDA wheels for
  `llama-cpp-python` are compiled on newer distributions and will not load against Ubuntu 20.04's
  glibc, and the plain wheel is CPU-only. `40-llama` therefore compiles `llama-cpp-python` locally
  against the toolkit detected on the machine. It is a one-time cost — nothing recompiles at run time.
- **Ownership is proven through `/proc`.** The launcher decides whether a process belongs to this
  checkout by resolving `/proc/<pid>/cwd`, a Linux-specific guarantee that lets it manage its own
  services without ever killing anything by port.

Newer Ubuntu releases (22.04, 24.04) work as well — the version-specific work in the bootstrap is all
about tolerating *older* hosts. Other Linux distributions are untested but nothing in the scripts is
Ubuntu-only beyond the assumptions above.

Users never touch the host: the VM has no graphical desktop, and Sedona is operated from a browser
over the institution's network from any OS.

### Prerequisites

The installer builds the whole runtime stack inside the project folder, but it cannot provide these.
Put them in place first.

| Requirement | Notes |
| --- | --- |
| **NVIDIA GPU + driver** | If `nvidia-smi` shows no GPU, setup stops with an explanation rather than quietly producing a CPU-only build. |
| **Node.js 18+ with npm** | The one dependency the bootstrap will not fetch for you. Node 18, 20 or 22+ all satisfy the locked Vite version. |
| **`curl` or `wget`** | Either one. Every download depends on it. |
| **Outbound internet** | First install only — see [Network requirements](#network-requirements). |
| **A non-root user account** | Do not run `start.sh` as root. Nothing is installed outside the project folder, so `sudo` is not required. |

Run the preflight checks before installing anything:

```bash
node --version      # v18, v20 or v22+
npm --version       # any version
curl --version      # or: wget --version
nvidia-smi          # a table listing at least one GPU, with driver and CUDA version
```

The CUDA toolkit itself is **not** a prerequisite — the installer reads the compute capability and
driver CUDA version off the machine and installs a matching toolkit inside the project folder.

### Reference deployment

| Component | Specification |
| --- | --- |
| OS | Ubuntu 20.04 LTS (server) |
| GPU | NVIDIA T4-8Q (8 GB VRAM slice) — workable for `gemma-3-4b-it`, but tight |
| Compute capability | 7.5, so the build targets `sm_75` |
| CUDA | 11.8 on the reference VM; the bootstrap picks a toolkit matching the installed driver's CUDA major version |
| vCPUs / RAM | 24 vCPUs / 64 GB |
| Python | 3.12+ (installed by the bootstrap) |
| Storage | Room for the Chroma store, ~2.8 GB of GGUF weights, the CUDA build toolchain and generated reports |

Running other GPU workloads on the same host alongside Sedona is not recommended: there is no
automatic CPU fallback, and 8 GB of VRAM is already tight for the chat model.

### Network requirements

The first installation is the only stage that needs the internet. It downloads a Miniforge Python and
the backend dependencies, CUDA toolkit packages, the GGUF model weights (~2.8 GB, from Hugging Face)
and the frontend npm packages. **An air-gapped first installation is not supported.** After that,
Sedona runs entirely locally — outbound access is an install requirement, not a running one.

In the reference deployment the VM sits on the institution's internal network and is not reachable
from the open internet; both SSH and the web interface require a VPN connection. Per-user
authentication sits in front of the application regardless, so VPN reachability is the outer boundary
and the user account is the access control that matters day to day.

## System at a glance

- React/Vite frontend in `FRONTEND/src`
- FastAPI application in `FRONTEND/api.py`
- HECVAT parsing, retrieval, assessment, consensus, follow-up and reporting in `BACKEND`
- Local llama.cpp chat and embedding servers
- Chroma persistent retrieval store under the configured data directory
- Local users, role-based access, cookie sessions, CSRF checks, and session
  ownership/assignment

A running system is four processes, all managed by `start.sh`:

| Port | Component | Role |
| --- | --- | --- |
| 8000 | Chat engine | `llama_cpp.server` running `gemma-3-4b-it` — evaluates each control against retrieved policy and evidence text and returns a JSON finding |
| 8001 | Embeddings engine | `llama_cpp.server` running `nomic-embed-text-v1.5` — embeds policy/evidence chunks at ingestion and control queries at assessment time |
| 8080 | API server | Authentication, sessions, uploads, reports, health |
| 5173 | Frontend | React single-page application served to the browser |

All four ports are environment-overridable. Chroma runs as an embedded Python library, so there is no
separate service to start for it.

### The models

| Role | Model | Format |
| --- | --- | --- |
| Chat / completion | `gemma-3-4b-it` | GGUF, Q4_K_M (4-bit) |
| Embedding | `nomic-embed-text-v1.5` | GGUF, f16 — 768-dimension vectors |

Both are served through `llama-cpp-python` with `n_gpu_layers = -1`, pushing every layer onto the
GPU; the chat server uses a 6144-token context window. The model does not perform retrieval itself —
the RAG pipeline retrieves the relevant policy text, HECVAT guidance and vendor evidence for each
control, and the model judges whether a gap exists.

Sampling temperature varies by operation:

| Operation | Temperature |
| --- | --- |
| Main assessment | 0.1 |
| Follow-up question generation | 0.2 |
| Follow-up reassessment | 0.0 |

Model weights are downloaded from Hugging Face during the bootstrap. **The downloader currently only
confirms the files are non-empty; it does not verify SHA-256 checksums**, so confirm integrity against
the published source before relying on a freshly downloaded model in production.

## Getting started

On a machine with nothing installed:

```bash
./start.sh
```

That is the whole procedure. If `start.sh` cannot find a Python that has Sedona's dependencies,
it runs `scripts/bootstrap.sh` first, then starts the services.

To install without starting anything, or to see what is missing:

```bash
./scripts/bootstrap.sh            # install whatever is missing
./scripts/bootstrap.sh --check    # report what is missing, change nothing
./scripts/bootstrap.sh --force    # re-run every step from scratch
```

`--check` exits **1** on a fresh machine. That means "components are missing", not that the check
failed; re-run it after installing and it should exit 0.

Then open the URL `start.sh` prints and sign in.

Do not run `start.sh` as root.

### Creating the first administrator

Sedona has no default account and no default password. The first administrator is created from three
environment variables, read **only once** — on the first API start, while the user database is still
empty. Export them in the shell you will start Sedona from, before that first start:

```bash
export SEDONA_BOOTSTRAP_ADMIN_USERNAME="sedona-admin"
export SEDONA_BOOTSTRAP_ADMIN_PASSWORD="ExamplePassphrase-2026!"
export SEDONA_BOOTSTRAP_ADMIN_DISPLAY_NAME="Sedona Administrator"
```

Those values are examples. Choose your own and never deploy with a placeholder password.

- The username and password must be set **together**, or the API stops rather than creating a
  half-configured account.
- Password: at least 12 characters, using at least three of lowercase, uppercase, digits, other.
- Username: 3–64 characters of lowercase letters, digits, `.`, `_` or `-`.
- Export the variables directly — **do not `source .env.example`**. Its display-name value is
  unquoted, so the shell tries to execute part of it. `start.sh` does not read `.env` at all.
- Remove the variables from the environment once the first start succeeds.

Self-service sign-up, where enabled, only ever creates a `viewer`.

### Completing the setup

Installation is not finished when the sign-in page loads. A new system has an **empty knowledge
base**, and every assessment stays blocked until an administrator ingests the policy corpus.

1. Sign in as the bootstrap administrator at the address `start.sh` printed.
2. Open the Admin-only **Knowledge Base** page and ingest the approved policy PDFs and
   `HECVAT_Template.xlsx` shipped with the release.
3. On the **User Access** page, create an Assessor account per staff member who will run assessments,
   and Viewer accounts for reviewers.
4. Confirm `curl "http://localhost:8080/health?strict=1"` returns 200. A 503 on a new installation
   almost always means step 2 has not been done.
5. Run one end-to-end assessment against a sample HECVAT and confirm PDF, PPTX and CSV all download.

### What to expect on first start

| Stage | Approximate time |
| --- | --- |
| Python, virtual environment and backend packages | Several minutes, network-dependent |
| CUDA build of `llama-cpp-python` | 10–30 minutes — it prints this warning itself; it is compiling, not hung |
| Model downloads (~2.8 GB) | Network-dependent |
| Frontend npm install | Several minutes, network-dependent |
| Chat and embedding engines load | ~1 minute; `start.sh` waits up to 8 minutes before pointing at `logs/llm.log` |
| API and frontend | Near-instant once the engines are up; 30 seconds allowed each |
| Every start afterwards | About a minute in total |

A healthy start prints a `SEDONA Risk Console` banner and three green readiness lines — engines, API,
frontend — then the address to open. The chat and embedding engines are reported together on one
line, so three lines is correct, not four. A component that was already up reports
`already healthy; reusing it` instead of `ready`.

## What the bootstrap installs, and where

Everything lands **inside this folder**. Nothing is written to `$HOME`, nothing needs sudo, and
deleting `.runtime/` undoes all of it.

| Path | Contents |
| --- | --- |
| `.runtime/venv` | the Python environment and Sedona's dependencies |
| `.runtime/conda` | package manager, only used to fetch the CUDA toolkit |
| `.runtime/cuda` | the CUDA toolkit — a compiler, used once at install time |
| `.runtime/.stamps` | which steps have completed |
| `models/` | the GGUF chat and embedding weights |

Steps run in order and each one is skipped when the thing it installs already works:

| Step | Does |
| --- | --- |
| `10-python` | finds a suitable Python or installs one, then creates the venv |
| `20-requirements` | installs `BACKEND/requirements.txt` |
| `30-cuda` | detects the GPU and installs a matching CUDA toolkit |
| `40-llama` | compiles `llama-cpp-python` against that toolkit |
| `50-models` | downloads the GGUF model files |
| `60-frontend` | installs the frontend npm packages |

A step is judged by whether it actually works, not by whether a marker file exists, so a
half-finished or partly deleted install repairs itself on the next run rather than being
skipped.

### GPU detection

The CUDA version and GPU architecture are read off the machine rather than hardcoded:

- compute capability from the GPU (a T4 reports 7.5, so the build targets `sm_75`), falling
  back to a card-name table where `nvidia-smi` is too old to report it;
- the CUDA toolkit chosen **inside the driver's own CUDA major line**.

That last point is the constraint that matters. NVIDIA's minor-version compatibility means a
binary built against 11.8 runs on a driver that only advertises 11.0 — which is why this works
on a 450-series driver. Crossing a major version does not work: a CUDA 12 binary will not load
against an 11.x driver, so it is never attempted.

If there is no GPU, the bootstrap **stops with an explanation** instead of quietly producing a
CPU-only build. A full assessment takes roughly four hours on CPU against minutes on a GPU, and
finding that out halfway through a run is worse than being told up front. To ask for it
deliberately:

```bash
SEDONA_FORCE_CPU=1 ./scripts/bootstrap.sh
```

The compile takes 10–30 minutes and happens once. Nothing recompiles at run time.

## Service lifecycle

| Command | Effect |
| --- | --- |
| `./start.sh` | Start whatever is down, reuse whatever is healthy. Reused services are not owned by this run, so `Ctrl-C` does not stop them. |
| `./start.sh --adopt` | Same, but take ownership of services already running, so `Ctrl-C` stops them. Covers the API and frontend unless `--engines` is added. |
| `./start.sh --stop` | Stop this checkout's API and frontend. |
| `./start.sh --stop --engines` | Also stop the chat and embedding servers. Expect a multi-minute model reload next start. |
| `./start.sh --restart-api` | Replace only the API process, after a backend code change. |

`start.sh` starts four things: the chat model server, the embedding server, the API, and the
frontend. It reuses any that are already healthy, so a bare run is a safe health check.

**Ownership is proven before anything is signalled.** A process counts as this checkout's only
when `/proc/<pid>/cwd` resolves inside this folder. Nothing is ever killed by port, so a second
Sedona elsewhere on the host, or a hand-started model server, is never disturbed.

`Ctrl-C` therefore stops only what the terminal actually owns. A service that was already healthy
was reused, not owned, and keeps running — use `--adopt` to take ownership, or `./start.sh --stop`
from any terminal when the original one is gone. Closing the terminal window is not a clean shutdown.

Backend changes need `--restart-api`; there is no `--reload`. Use the flag rather than killing
and relaunching by hand: uvicorn holds the port for a moment after exiting, so a naive restart
races, the new process dies on an address-in-use error, and the API stays down while the
frontend proxy returns 500s. `--restart-api` waits for the port to actually free, then relaunches
and polls `/health`.

Frontend changes hot-reload; no restart needed.

`run_gpu.sh` is idempotent on its own too: a port that is already serving is left alone, so a
manually started engine on `:8000` is reused rather than clobbered, and only the servers it started
are torn down on `Ctrl-C`. To force an engine restart, stop them first with
`./start.sh --stop --engines`.

### Configuration

Paths, ports, model files, origins and data locations are all environment-overridable — see
`.env.example`. The useful ones:

| Variable | Purpose |
| --- | --- |
| `SEDONA_PYBIN` | use a specific interpreter instead of searching |
| `SEDONA_DATA_DIR` | relocate all persistent state at once |
| `SEDONA_API_PORT` / `SEDONA_FRONTEND_PORT` | change ports (default 8080 / 5173) |
| `SEDONA_LLM_PORT` / `SEDONA_EMBED_PORT` | change engine ports (default 8000 / 8001) |
| `SEDONA_MODEL_DIR` | where the GGUF files live |
| `SEDONA_RUNTIME_DIR` | where the bootstrap installs |
| `SEDONA_LOG_DIR` | where `llm.log`, `api.log` and `frontend.log` are written |
| `SEDONA_COOKIE_SECURE` | set true when Sedona is served over HTTPS |
| `SEDONA_FORCE_CPU` | build without CUDA |

Storage paths are anchored to the project root, never the working directory, so it does not
matter where you launch from.

There is no configuration screen and no configuration API: environment and service configuration is
a deployment responsibility carried out on the host, not something edited from inside the app.

## Main workflow

1. An administrator indexes approved institutional policies and the HECVAT guidance template.
2. An assessor uploads a filled HECVAT and names the vendor or service.
3. Before starting, the assessor may attach the vendor's SOC 2 report or other supporting PDFs.
   Those documents are isolated to that session and never enter the institution-wide store.
4. Sedona assesses each institutionally applicable control. A control whose runs do not produce
   a usable result is excluded from the scores and flagged for manual resolution rather than
   being guessed at.
5. The assessor reviews the follow-up questions, attaches further evidence, answers or skips,
   and resolves flagged controls with a recorded justification.
6. Sedona generates the JSON/API, CSV, PDF and PPTX outputs from one canonical finding set, so
   the four cannot disagree.

The PDF and CSV carry every control in full. The PPTX is a fixed-length executive briefing —
title, recommendation, key components, severity distribution, top risks, assurance and
limitations, next steps — and does not grow with the size of the assessment.

### Inputs

| Input | Accepted | Notes |
| --- | --- | --- |
| HECVAT | `.xlsx`, `.xlsm` | Parsed at upload, so a bad workbook is caught on the Upload page rather than becoming a failed session. Two guards run: one rejects a workbook that is over 90% blank, the other rejects one whose formulas were never evaluated. `.xls` is not reliably supported. |
| Supporting evidence | PDF only | Optional. Isolated to its session; never enters the institution-wide knowledge base. |
| Policy corpus | PDF + `HECVAT_Template.xlsx` | Ingested once by an administrator through the Knowledge Base page. |

Uploads are capped at 50 MB per file. Only Admin and Assessor accounts can upload.

### Findings and outputs

Gaps are reported at five severities — **VERY HIGH**, **HIGH**, **MEDIUM**, **MINOR**, **LOW** — and
filterable on the Results page. Reports download as `RiskAssessment_<Vendor>.pdf` and
`RiskBriefing_<Vendor>.pptx` with a matching CSV, so no manual renaming is needed before sharing. The
download buttons return a file only once the session status is `Complete`; earlier clicks get a 409,
which the interface reports as "not ready yet".

Only one assessment runs at a time, **system-wide** rather than per user. Assessments continue
server-side if the browser is closed — reopen the session from the History page to get back to it.
Saved follow-up answers are resumable at any time; the initial scan cannot be paused, only cancelled,
and cancelling permanently deletes the session's data and uploaded HECVAT.

## Roles and security

| Role | Can |
| --- | --- |
| **Admin** | Everything an Assessor can, plus the two admin-only screens: User Access and Knowledge Base |
| **Assessor** | Upload HECVATs and evidence, run assessments, answer follow-ups, generate and download reports, manage their own sessions |
| **Viewer** | Read-only. Cannot upload, start, answer, cancel or delete. Can open only completed sessions specifically assigned to them |

Sign-in is per user. Passwords are stored as scrypt hashes with a per-user salt; a successful sign-in
issues an **HttpOnly** session cookie that page scripts cannot read; state-changing requests are
additionally protected by a **CSRF token**; sessions expire after a configurable number of hours
(eight by default); and account events are written to an audit table. Self-registration always
creates a Viewer, and promotion is a deliberate Admin action. The last active administrator cannot be
disabled or deleted, and an administrator cannot delete their own account.

The interface is a React single-page application, so the browser needs JavaScript and cookies
enabled. A current Chrome or Safari is recommended.

## Health and logs

`GET /health` reports the real state of the chat server, the embedding server and the vector
store, plus whether an assessment can actually run. It returns HTTP 200 even when degraded, so
that `start.sh` can distinguish "the API is up" from "the API is healthy"; the body carries the
truth — component states, a `can_assess` flag, and the reasons when something is wrong. Pass
`?strict=1` to get a 503 when degraded instead.

```bash
curl "http://localhost:8080/health?strict=1"
```

Logs are written to the configured log directory (`logs/` by default): `llm.log` for the two
inference engines, `api.log` for the backend, `frontend.log` for Vite.

### Troubleshooting

| Symptom | Check |
| --- | --- |
| Setup stops on GPU detection | No NVIDIA GPU visible to `nvidia-smi`. Provision one, or accept `SEDONA_FORCE_CPU=1` and ~4 hours per assessment. |
| `npm not found` / frontend step stops | Install Node 18+ and re-run; the bootstrap will not fetch Node for you. |
| The llama build looks hung | The CUDA compile legitimately takes 10–30 minutes and says so before it starts. |
| CUDA loading errors | Confirm the driver's CUDA major version matches the toolkit the bootstrap selected, and that the GPU is visible to the VM. |
| Missing `llama_cpp.server` | `llama-cpp-python` must be installed with the `[server]` extra. |
| Ports already in use | `./start.sh --stop --engines` releases 8000/8001/8080/5173 cleanly before relaunching. |
| Health degraded / assessments rejected | Almost always an un-ingested knowledge base. An empty collection means the RAG pipeline retrieves no context. |
| `No Python with Sedona's dependencies found` | Run `./scripts/bootstrap.sh`, or point `SEDONA_PYBIN` at an interpreter that already has them. |
| An engine never reports ready | Read `logs/llm.log` before assuming the whole system failed. |

## Known limitations

Stated plainly, because a showcase that hides them is not much of a showcase:

- **Accuracy is a target, not a measured result.** 90% correctness against a manually evaluated
  reference is the goal for gap findings and risk statements. An accuracy comparison module exists in
  the codebase but is not wired into the application, and no reference dataset or results ship with
  the release.
- **Timing figures are informal observations.** Processing time scales with the number of controls in
  the HECVAT. Report generation is quick (~20–60 seconds) only when no follow-ups were answered; each
  answered follow-up triggers a fresh retrieval-and-generation pass at roughly 8 seconds per control,
  so a fully answered 88-control HECVAT can take twelve minutes or more. Each session record stores
  the real elapsed time — treat that, not these estimates, as the evidence.
- **Not every answered follow-up triggers another model pass.** If policy similarity for the
  follow-up is too low, the original finding is kept without calling the model.
- **No automatic CPU fallback.** Both engines push every layer to the GPU. CPU is available only by
  deliberately setting `SEDONA_FORCE_CPU=1`.
- **Model downloads are not checksum-verified** — only checked for being non-empty.
- **A clean-VM acceptance test has not yet been recorded** against this release. The installation
  procedure above is documented as intended rather than as confirmed.

Sedona does not make a vendor compliant. It produces decision support that requires qualified
human review.
